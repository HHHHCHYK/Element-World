# Fix Mojibake Comments

本项目的 Windows 工作区里，UTF-8 编码的中文注释常被编辑器或工具以 GBK/GB18030 解读，产生 mojibake（如「懒加载」→`鎳掑姞载?`、「修改」→`鏇存敼`）。本技能用于把这些注释还原成正确中文，同时保证**可执行代码逐字节不变**。

## 核心约束

**只改注释，不碰代码。** 这是不可妥协的红线。如果还原过程中动了任何变量、运算、控制流、括号、import、注解，就算任务失败。

## 识别 mojibake

UTF-8 中文被 GBK 解读后的典型特征：
- 出现 `鎳` `鏇` `鍒` `濡` `鐢` `瀛` `涓` 等高频 GBK 字符
- 句尾常带 `?` 或 `锛?`（UTF-8 字节序列被 GBK 截断所致）
- 注释「看起来像乱码汉字」而非有意义的句子

若整个文件都是这种情况，按下面流程处理；若只有个别行，同样适用。

## 还原方法（重要：解码不一定可逆）

> ⚠️ **实证结论**：mojibake 转换**不总是可逆**。把乱码按 GBK 解码只对部分注释成立，取决于原 UTF-8 字节是否恰好构成合法 GBK 序列。若出现 `�`（U+FFFD）说明字节已损坏，无法靠纯字节转换还原。

因此采取「解码辅助 + 代码逻辑核对」双保险，而非单靠解码。

### 1. 读取并确认乱码范围

先 Read 目标文件，定位所有乱码注释的行号。区分两类：
- **行内注释**：`if (x == null) {//绌哄€兼鏌?`（代码后紧跟注释）
- **块注释**：`/* 杩欎竴姝ヤ负... */`

### 2. 尝试解码（辅助参考，不可全信）

mojibake 文件本身是 UTF-8 编码（内容是乱码字符）。尝试把乱码字符串按 GBK 重新编码再按 UTF-8 解码，看能否还原原文：

```powershell
# 脚本文件方式执行（避免 bash 把 $ 展开成空）
$gbk = [System.Text.Encoding]::GetEncoding('GB18030')
$utf8 = [System.Text.Encoding]::UTF8
$moji = [System.IO.File]::ReadAllText('<文件路径>', $utf8)   # 乱码字符串
$restored = $utf8.GetString($gbk.GetBytes($moji))             # 尝试还原
```

> 注意方向：是「UTF-8 读出乱码串 → GBK 编码成字节 → UTF-8 解码」，**不是**对文件字节直接 GBK 解码（后者得到的是双层乱码）。实测约 80% 注释可还原，含 `�` 的行会失败。

> Plan mode 下 PowerShell 读写会被拦截：先只读探查，解码步骤留到执行阶段。

### 3. 以代码逻辑为最终依据

解码失败或解码出的词需用代码语义核对。mojibake 字符的偏旁部首也能提供线索（如「鎳掑姞杞」含「懒/加/载」的偏旁 →「懒加载」），再对照上下文确认。

某些乱码还原出的词与代码实际逻辑不符（实战中，某行注释解码为「护盾」，但该代码块是 attacker 增伤计算）。**以代码逻辑为准**修正措辞，并在最终总结里标注这类修正。

## 改写策略：优先整体 Write，慎用逐条 Edit

**不要逐条用 Edit 匹配乱码字节。** mojibake 的多字节序列很难精确复制到 `old_string`，极易匹配失败（本次实战中第 3 处 Edit 就因字节不一致失败）。推荐：

1. **首选整体 Write**：基于已 Read 的完整文件内容，重写整个文件，只替换注释、代码逐字保留。比逐条匹配稳定得多。
2. Write 时确保以 **UTF-8 无 BOM** 写入（与项目惯例一致）。
3. 行内注释统一格式：代码与 `//` 之间留一个空格（`{ // 中文`），比紧贴的 `{//乱码` 更清晰，且不属「改代码」。

## 验证（必须全部执行）

### a. 代码零改动验证

去除注释后逐行对比，确认可执行代码与改动前完全一致：

```bash
diff <(git show HEAD:<路径> | sed -E 's|//.*$||; s|/\*.*\*/||' | sed '/^\s*$/d; /^\s*\*/d; /^\s*\/\*/d') \
     <(sed -E 's|//.*$||; s|/\*.*\*/||' <路径> | sed '/^\s*$/d; /^\s*\*/d; /^\s*\/\*/d')
```

输出应只剩注释行（被 sed 清空后为空行而被过滤）——**任何非注释代码行的差异都意味着动了代码，必须回退修正。**

### b. 空白与行尾检查

```bash
git diff --check
git status --short
```

注意行尾：`.gitattributes` 规定 `*.java`/`*.md` 统一 LF。若 Write 后文件变成 CRLF，会触发 `CRLF will be replaced by LF` 警告。Git 会在提交时自动归一化，但工作区应尽量保持一致——检查并说明。

### c. 编译验证

完整 `build` 在 Loom 首次解包时可能超时（本项目实战中超过 10 分钟）。改用聚焦的编译任务，更快且足够：

```bash
./gradlew :compileJava --console=plain --rerun-tasks
```

`--rerun-tasks` 确保不命中 `UP-TO-DATE` 缓存，真正重新编译。若注释改动引入了 `/* 未闭合` 等错误会在此暴露。

## 陷阱清单

| 陷阱 | 说明与对策 |
|------|-----------|
| **解码不可逆** | 把乱码按 GBK 解码只对部分注释成立；出现 `�`（U+FFFD）说明字节已损坏，无法靠字节转换还原，须靠代码逻辑推断 |
| **解码方向易反** | 正确方向是「UTF-8 读乱码串 → GBK 编码 → UTF-8 解码」；对文件字节直接 GBK 解码会得到双层乱码 |
| Edit 匹配乱码失败 | mojibake 多字节难以精确复制；改用整体 Write |
| build.gradle 无编码设置 | 项目未显式设 `compileJava` 编码，源码默认按平台编码——务必以 UTF-8 写入 |
| Git Bash 终端显示中文为 mojibake | 这是**显示问题**，不代表文件字节有误；以文件字节或编译结果为准（AGENTS.md 已说明） |
| **bash 吃掉 PowerShell 的 `$`** | `powershell -Command "..."` 在 bash 双引号里 `$var` 会被 bash 展开成空；改用脚本文件 + `powershell -File` 或 `& '<path>.ps1'` |
| **Write 工具写中文脚本可能坏编码** | 写含中文的 `.ps1` 时，若底层按非 UTF-8 落盘，PowerShell 解析会崩；脚本尽量只放 ASCII（中文样本从源文件读） |
| Plan mode 拦截 PowerShell | Plan mode 只允许只读工具，解码用的 PowerShell 会被拦；先只读探查，执行阶段再解码 |
| 还原词与代码逻辑矛盾 | 以代码逻辑为准，并标注告知用户 |

## 交付总结要点

向用户报告时包含：
- 还原了多少处注释（行内/块注释分类）
- 是否有「还原词与代码语义不符」的修正（如「护盾」→「增伤」），逐条列出
- 三项验证结果（代码零改动 / `diff --check` / `:compileJava`）
- 跳过的检查（如完整 `build` 超时）及理由
