## [BUG] 持续反应触发攻击漏算增伤/减抗乘区

### 现象
触发感电（ELECTRO_CHARGED）或燃烧（COMBUSTION）的那一次攻击，
其伤害 `amount` 既未按"增幅反应"走乘区，也未按"无反应"做增伤×减抗改写，
带着原始数值直接结算。相比之下，触发蒸发/融化的攻击会走增伤乘区，
不发生反应的攻击会走 `amount * (1+增伤) * (1-减抗)`。

### 根因
`LivingEntityMixin.applyDamageModifyArgs`（src/main/java/com/elementworld/mixin/livingEntity/LivingEntityMixin.java:132-151）
的二分逻辑：

    if (reaction != null) {
        if (reaction instanceof AmpReaction ampReaction) {
            amount = amount * (1 + baseMul) * 精通 * 增伤 * 减抗;   // 增幅
        } else {
            reaction.apply();   // 其他反应（含持续反应）
        }
        // ↑ 持续反应 apply() 是空操作（继承 Reaction 父类），
        //   且 amount 在此分支内未被任何乘区改写
    } else {
        amount = amount * (1 + 增伤) * (1 - 减抗);   // 无反应反而改写了 amount
    }

持续反应（ElectroCharged / Combustion）的伤害逻辑全部写在 `tick()` 里，
`apply()` 为空实现。因此触发持续反应的攻击进入了 `reaction != null` 分支，
却因空 apply() 而未获得任何乘区加成，也没有走无反应分支的改写。

### 相关：空 apply() 本身是设计取舍
持续反应把伤害放 tick()（周期性 CD），apply() 留空属于"持续型"语义，
与剧变反应（apply() 内一次性 damage）的范式分野。空 apply() 本身不算 bug，
真正的问题是 caller 二分逻辑导致的 amount 漏算。

### 证据
- 制造点：ElementContainer.applyElement 返回持续反应实例
  （reactions.put + return reaction）
- caller 二分：LivingEntityMixin.java:132-151（有 attacker）/ :154-170（无 attacker）
- 空 apply：ElectroCharged.java、Combustion.java 均未重写 apply()，
  继承 Reaction.java 父类的空实现
- tick 驱动：LivingEntityMixin.java:52-59 → ElementContainer.tick()（:161-188）
  → ElectroCharged.tick() / Combustion.tick()

### 修复决策点（待定）
1. caller 二分逻辑是否重构（在 LivingEntityMixin，超出"仅 applyElement"重构范围）？
2. 是否给持续反应补 apply() 让首跳生效？这会改变游戏行为，属数值/设计改动。
3. 感电 CD 从 20 起算导致首跳延迟约 21 tick（~1秒），是否需调优？
   （偏慢，但属数值问题，非结构 bug）

### 范围归属
修复落在 LivingEntityMixin.applyDamageModifyArgs，不在本次 applyElement 重构范围内。
本轮 applyElement 重构须保留"持续反应返回非 null + 空 apply()"的当前行为。

## 同期发现（关联风险）

### [风险] 扩散是唯一的"反应→新反应"传染路径
扩散（Swirl）通过反应伤害源 `setElement(...)` 写入被扩散元素、且**不设**
`setCannotApply`，使被扩散实体进入 `applyElement`，实现元素扩散传染。
其他剧变/持续反应的伤害源都设了 `setCannotApply` 或不带 `setElement`，
不会二次附着。重构任何反应 handler 时，扩散的两个伤害源设置（setElement +
不设 setCannotApply）必须原样保留，否则会破坏"只有扩散传染"的设计。

### [风险] 持续反应状态标志与 Map 双重冗余
`ElementContainer.isElectroCharged` / `isCombustion` 布尔标志，与
`reactions` Map 是否含对应 key 表达同一信息，但分散维护。
`applyElement` 制造时设 `isElectroCharged=true` + `reactions.put`，
`tick()` 读取时两者都要检查。任何一处忘记同步会让 tick() 读到
`isElectroCharged=true` 但 Map 为空（或反之）。这是着力点 3 重复代码的
根源，重构时应优先用 `reactions.containsKey(...)` 取代布尔标志。

### [风险] 持续反应状态不持久化
`loadPersistentState` 末尾调用 `clearRuntimeReactionState()`
（ElementContainer.java:472-477）直接 `reactions = null`。
存档只保存元素附着快照，感电/燃烧等持续反应在重载后丢失，
须由后续游戏逻辑重建。属已知设计，但与"持久化系统"的整体完备性相关，
后续若要完整持久化需补持续反应序列化。

### [风险] 半成品反应
- Crystallize / BloomReaction / Catalyze（reaction 包）为空壳：
  只有构造器，`apply()` 继承父类空实现。其中 BLOOM/CATALYZE 有触发路径
  但 .apply() 空操作，CRYSTALLIZE 同样空操作。
- SHATTER / BURGEON / HYPERBLOOM 既无触发逻辑也无实现：
  ReactionType 枚举中有，工厂可映射，但 applyElement 无路径返回它们；
  TFReaction.apply() 的 SHATTER 落到 default 分支打 warn。
- 命名冲突：elements/Catalyze（激元素，有衰减逻辑）与
  reaction/Catalyze（激化反应，空壳）同名不同包，重构引用时易混淆。
