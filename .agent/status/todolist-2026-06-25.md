## [BUG] 持续反应触发攻击漏算增伤/减抗乘区

> ✅ **已修复（2026-06-25）** — 由阶段F「有元素即走乘区」逻辑消解。
> 新逻辑下，触发感电/燃烧等非增幅反应的那次攻击，amount 走 `(1+增伤)×(1-减抗)`（有 attacker）
> 或 `(1-减抗)`（无 attacker），不再带原始数值直接结算。与蒸发/融化（额外乘倍率×精通）、
> 无反应（同样走乘区）三者统一。验证待手动回归。

### 现象
触发感电（ELECTRO_CHARGED）或燃烧（COMBUSTION）的那一次攻击，
其伤害 `amount` 既未按"增幅反应"走乘区，也未按"无反应"做增伤×减抗改写，
带着原始数值直接结算。相比之下，触发蒸发/融化的攻击会走增伤乘区，
不发生反应的攻击会走 `amount * (1+增伤) * (1-减抗)`。

### 根因（重构前）
`LivingEntityMixin.applyDamageModifyArgs` 的二分逻辑：

    if (reaction != null) {
        if (reaction instanceof AmpReaction ampReaction) {
            amount = amount * (1 + baseMul) * 精通 * 增伤 * 减抗;   // 增幅
        } else {
            reaction.apply();   // 其他反应（含持续反应）
        }
        // ↑ 持续反应 apply() 是空操作（继承 Reaction 父类），
        //   且 amount 在此分支内未被任何乘区改写
    } else {
        amount = amount * (1 + 增伤) * (1 - 减抗);   // 无反应反而改写了 amount
    }

持续反应（ElectroCharged / Combustion）的伤害逻辑全部写在 `tick()` 里，
`apply()` 为空实现。因此触发持续反应的攻击进入了 `reaction != null` 分支，
却因空 apply() 而未获得任何乘区加成，也没有走无反应分支的改写。

## 同期发现（关联风险）

### [风险] 扩散是唯一的"反应→新反应"传染路径 — ✅ 已在 handler 中原样保留
扩散（Swirl）通过反应伤害源 `setElement(...)` 写入被扩散元素、且**不设**
`setCannotApply`，使被扩散实体进入 `applyElement`，实现元素扩散传染。
重构后 Swirl 的传染链在 `ReactionTable.swirl()` handler 中保留（create+apply）。

### [风险] 持续反应状态标志与 Map 双重冗余 — ✅ 已缓解
重构后 `tick()` 统一通过 `ensureReactionsMap()` + `containsKey` 读取感电/燃烧，
并增加「Map 无实例则清布尔标志」的兜底同步。布尔标志 `isElectroCharged`/`isCombustion`
保留为快速通道，但不再产生失同步导致 tick 漏读的问题。

### [风险] 持续反应状态不持久化 — ⏳ 未处理（plan 明确「本次不做」）
`loadPersistentState` 末尾调用 `clearRuntimeReactionState()` 直接 `reactions = null`。
存档只保存元素附着快照，感电/燃烧等持续反应在重载后丢失，
须由后续游戏逻辑重建。本次未动。

### [风险] 半成品反应 — ⏳ 未处理（plan 明确「本次不做」）
- Crystallize / BloomReaction / Catalyze（reaction 包）仍为空壳（仅构造器，apply 空继承）。
  重构后这些组合在 handler 内 `Reaction.create(...)` 但 apply 为空操作，行为与重构前一致。
- SHATTER / BURGEON / HYPERBLOOM 仍无触发路径与实现。
- 命名冲突：elements/Catalyze（激元素，有衰减逻辑）与
  reaction/Catalyze（激化反应，空壳）同名不同包，已通过显式 import 处理。
